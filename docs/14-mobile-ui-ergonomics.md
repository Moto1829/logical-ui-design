# 第14章 モバイルUIとタッチ操作
## 第14章 モバイルUIとタッチ操作

モバイルUIでは、画面が小さいことより、操作条件が厳しいことが重要です。片手で持ち、移動中に見て、キーボード表示で画面が狭くなり、通信も不安定かもしれません。ここでは、モバイル特有の制約を前提にどう設計するかを整理します。

## 1. モバイルでは視認性と到達性を同時に考える

デスクトップでは見やすければ十分だった要素も、モバイルでは押しやすさまで考えなければなりません。特に重要なのは次の3点です。

- タップ対象が十分な大きさか
- 親指で届きやすい位置にあるか
- 誤タップしやすい密度になっていないか

小さいリンクや詰まりすぎたボタンは、理解できても操作できません。

押しやすさを考えると、次に重要になるのは画面内での役割分担です。特にモバイルでは、上部と下部で向いている役割が違います。

## 2. 画面上部と下部では役割を分ける

モバイルでは、画面上部は見出しや状態確認に向きますが、主要操作は下部の方が届きやすいことが多いです。そのため、情報と操作の役割を分けると扱いやすくなります。

例:

- 上部: 画面タイトル、状態、検索結果数
- 下部: 主要CTA、タブ切替、確定操作

逆に、最も頻繁に押すボタンが右上に固定されていると、片手操作では負担が大きくなります。

## 3. モバイルフォームでは入力中の画面変化を考える

フォームでは、ソフトウェアキーボードが表示されると、使える高さが一気に減ります。そのため、入力中に次の項目や送信ボタンが見えなくなる問題が起きやすくなります。

見るべき点:

- ラベルが常に見えるか
- 入力中の文脈が保たれるか
- 次の操作へ進みやすいか

プレースホルダーだけをラベル代わりにすると、入力開始後に何の項目か分からなくなるため、モバイルでは特に不利です。

## 4. スクロール前提でも優先順位は必要である

モバイルでは縦スクロールが前提ですが、だからといって情報の順序を軽視してよいわけではありません。最初に見える範囲に何を置くかは依然として重要です。

基本:

- 最上部には画面の目的と現在地を置く
- 最初の一画面で主要判断ができるようにする
- 補助情報は後半へ送る

「あとで読めばよい」と考えて説明を長く積むと、主要操作が下に追いやられます。

## 5. 移動中や片手操作を前提にする

実際のモバイル利用では、落ち着いた環境で両手操作できるとは限りません。通知や中断も多く、短時間で再開できることが重要です。

そのため、次の点が有効です。

- 状態が途中で失われない
- 入力途中でも再開しやすい
- 1画面内でやることが多すぎない

モバイルの使いやすさは、見た目の省スペース化ではなく、途切れやすい利用に耐えられるかで決まります。

ここまでの条件をまとめると、良いモバイルUIの基準が見えてきます。次は、実務で確認しやすい形で整理します。

## 6. 良いモバイルUIの条件

良いモバイルUIは、次の問いに答えやすい状態です。

- いま何をする画面か
- 主要操作はどこにあるか
- 片手でも無理なく操作できるか

この3つが明確なら、狭い画面でも迷いと誤操作を減らせます。

モバイルUIが悪いと、理解できるのに操作できない状態が起きます。これは単なる見づらさではなく、片手操作や移動中利用という現実の利用条件に合っていないことが原因です。

- 誤タップが増える: 小さすぎる要素や近すぎる配置で押し間違える
- 入力が中断しやすい: キーボード表示で文脈や送信導線が消える
- 操作を先延ばしにする: 片手ではやりにくく、後でやろうと離脱する
- 再開コストが高い: 途中状態が保たれず、短時間利用に向かない

モバイルUIでは、画面の狭さより利用状況の厳しさを前提にすることが重要です。最後に、この章の要点をまとめます。

## 7. この章の要点

- モバイルでは見やすさだけでなく押しやすさも設計対象である
- 画面上部は情報、下部は主要操作という役割分担が有効である
- フォームではキーボード表示後の状態変化を考える
- スクロール前提でも最初の一画面の優先順位は重要である

## 迷いやすい判断

**主要な操作を画面の下部に固定するか**

購入や送信のように、画面の目的となる操作が1つに決まっている場合は、下部に固定すると親指で届きやすく、スクロールしても見失いません。ただし、固定した領域はコンテンツの表示領域を狭め、キーボードを開いたときに入力欄を隠すことがあります。固定するのは1つの主要な操作に限り、入力中は隠れないようにします。

**押せる領域の大きさをどこまで確保するか**

指で押す要素は、見た目が小さくても、押せる領域を44〜48px四方程度確保するのが目安です。WCAG 2.2のAAでは、最低24px四方（または十分な間隔）が求められています。見た目の大きさと、押せる領域の大きさは分けて考えられます。

## レビューコメントの例

「一覧の各行にある削除アイコンが、押せる領域が20px程度で、編集アイコンと隣接しています。移動中に操作すると押し間違えやすくなります。押せる領域を44px程度に広げ、削除は詳細画面か左右のスワイプに移すことを提案します。」

「入力欄に触れるとキーボードが開き、画面下部に固定された送信ボタンが入力欄に重なります。入力中は固定を解除するか、入力欄が隠れない位置までスクロールさせてはどうでしょうか。」

## 演習

次のモバイル画面について、問題点を3つ挙げ、それぞれの改善案を考えてください。

> 乗換案内アプリ。出発駅と到着駅の入力欄が画面上部にあり、「検索」ボタンは右上の小さなアイコン。結果画面の「戻る」は左上の端にだけある。片手で電車のつり革を持ちながら使われることが多い。

??? note "解答例"
    - 検索ボタンが右上の小さなアイコンで、片手では届きにくい。入力欄のすぐ下に、幅の広い「検索」ボタンを置く
    - 戻る操作が左上の端にしかなく、片手では届かない。画面の端からのスワイプで戻れるようにするか、下部に操作を置く
    - 片手での利用が多いのに、主要な操作が上部に集まっている。よく使う操作（駅の入れ替え、検索）を親指の届く範囲に移す
