# 第29章 一貫性とデザインシステム
## 第29章 一貫性とデザインシステム

ここまでの章では、画面や部品ごとの設計を扱ってきました。しかし、1つ1つの画面が良くできていても、画面ごとに見た目や言葉や振る舞いが違えば、ユーザーは画面を開くたびに使い方を学び直すことになります。この章では、サービス全体の一貫性と、それを保つための仕組みであるデザインシステムを扱います。

## 1. 一貫性は学習を再利用させる

ユーザーは、一度覚えた使い方を他の場面でも使おうとします。ある画面で「青いボタンが主要な操作」と学んだら、別の画面でも同じように解釈します。一貫性とは、この学習を無駄にしないことです。

一貫性には2つの方向があります。

- 内部の一貫性: 同じサービスの中で、同じ意味のものが同じ見た目と振る舞いをする
- 外部の一貫性: 他の多くのサービスで定着している慣習に従う

外部の一貫性については、ヤコブの法則と呼ばれる考え方が知られています。ユーザーは時間の大半を他のサービスで過ごしているため、自分たちのサービスも他と同じように動くことを期待する、というものです。ロゴを押すとトップに戻る、右上にアカウントのメニューがある、といった慣習は、理由がない限り崩さない方がよいとされます。

## 2. 「似ているが違う」が最も危ない

一貫性が崩れたとき、最も問題になるのは、見た目がまったく違う場合ではありません。見た目がほとんど同じなのに、意味や振る舞いが少しだけ違う場合です。

起きやすい例:

- 同じ青のボタンが、ある画面では保存、別の画面では削除に使われている
- 「キャンセル」が、ある画面では入力を破棄し、別の画面では予約を取り消す
- 日付の表記が「2026/10/01」「10月1日」「1 Oct」と画面ごとに違う
- 同じ×のアイコンが、閉じる場合と削除する場合の両方に使われている

第2章で扱った類同の原則により、ユーザーは似た見た目のものを同じ役割だと解釈します。役割が違うのに見た目が似ていると、ユーザーは区別の仕事を押し付けられ、誤操作が起きます。

## 3. デザイントークンで判断を固定する

一貫性を人の注意力だけで保つことはできません。画面が増え、関わる人が増えるほど、少しずつずれていきます。そこで、色や余白などの値に名前を付けて共通化する方法が使われます。これをデザイントークンと呼びます。

トークンの名前は、見た目ではなく役割で付けます。

| 見た目で名付けた例 | 役割で名付けた例 |
| --- | --- |
| `red-600` | `color-danger` |
| `blue-500` | `color-action-primary` |
| `spacing-16px` | `space-section-gap` |

役割で名付けると、「この赤は危険を表しているのか、単に強調したいのか」という判断を、使う人が毎回しなくて済みます。また、ダークモードのように見た目を切り替えるときにも、役割の名前はそのままで値だけを変えられます。

余白や文字の大きさも、自由な値ではなく、決まった段階の中から選ぶようにします。段階が決まっていると、画面ごとに微妙に違う余白が生まれにくくなります。

## 4. 部品の単位と例外の扱いを決める

デザインシステムの中心は、ボタン、入力欄、モーダルなどの共通部品です。共通部品には、見た目だけでなく次の内容まで含めます。

- 使う場面と使わない場面
- 状態ごとの見た目（通常、ホバー、フォーカス、無効、読み込み中、エラー）
- 文言の書き方（第16章、第18章）
- アクセシビリティの要件（第6章、第15章）

見た目だけをそろえても、使い方の判断が人によって違えば、一貫性は保てません。「この場面ではモーダルを使わない」のような使わない場面の記述は、特に役に立ちます。

それでも、共通部品では対応できない場面は必ず出てきます。そのときは、黙って独自の部品を作るのではなく、理由を記録し、他でも必要なら共通部品に取り込む流れを決めておきます。例外が記録されずに増えると、やがて共通部品そのものが信用されなくなります。

## 5. デザインシステムは作るより運用する

デザインシステムは、一度作れば完成するものではありません。サービスの変化に合わせて更新し続ける必要があります。

運用で決めておくこと:

- 誰が変更を判断するか
- 新しい部品や変更の提案をどう受け付けるか
- 変更をどう周知し、既存の画面にどう反映するか
- デザインのデータと実装のコードを、どう一致させ続けるか

デザインツール上の部品と実装上の部品がずれていくと、デザインどおりに作ったはずなのに見た目が違う、という問題が起きます。両者を同じ名前で管理し、どちらかを変えたら、もう一方も変える流れを作ります。

## 6. 一貫したUIの条件

- 同じ意味のものが、どの画面でも同じ見た目、言葉、振る舞いをする
- 役割の違うものが、似た見た目になっていない
- 広く定着した慣習から外れるときは、それに見合う理由がある
- 色や余白が、役割で名付けた共通の値から選ばれている
- 共通部品に、使う場面、状態、文言、アクセシビリティの要件が含まれている

一貫性が崩れると、画面単位では見えない負担が積み重なります。

- 学習が進まない: 画面ごとに使い方を確かめ直すことになる
- 誤操作が起きる: 似た見た目の部品を、同じ役割だと思い込む
- 開発が遅くなる: 画面ごとに似た部品を作り直し、修正も個別に行うことになる
- 品質がばらつく: アクセシビリティなどの対応が、部品ごとに漏れる

一貫性は、ユーザーの学習と、作り手の判断の両方を節約する仕組みです。最後に、この章の要点をまとめます。

## 7. この章の要点

- 一貫性は、ユーザーが一度覚えた使い方を他の場面でも使えるようにする
- 最も危ないのは、見た目が似ているのに意味や振る舞いが違う状態である
- デザイントークンは、見た目ではなく役割で名付ける
- 共通部品には、使う場面、状態、文言、アクセシビリティまで含める
- デザインシステムは、変更の判断と周知の仕組みまで含めて運用する

## 迷いやすい判断

**一貫性を優先するか、その画面での最適を優先するか**

原則として一貫性を優先します。その画面だけを見れば別の見せ方が少し良く見えても、他の画面との違いを学ぶコストがそれを上回ることが多いためです。ただし、共通の見せ方ではその画面の主な作業が明らかに妨げられる場合は、例外として扱い、理由を記録します。

**他社の定番に合わせるか、独自の操作を作るか**

よく使われる操作（検索、ログイン、カート、設定など）は、定番に合わせます。ユーザーはその操作を他のサービスで学んできているからです。独自の操作は、そのサービスの中心的な価値に関わり、定番では実現できない場合に限ります。

## レビューコメントの例

「一覧画面の削除ボタンと、詳細画面の保存ボタンが同じ青の塗りつぶしになっています。利用者はこの青を主要な操作と学習しているため、一覧画面で削除を主要な操作と誤解する恐れがあります。削除には共通部品の危険操作のスタイルを使ってはどうでしょうか。」

「この画面だけ、日付が『10/1』という形式で表示され、他の画面の『2026年10月1日』と異なっています。年をまたぐデータで年が分からず、比較もしにくくなります。共通の日付表記に合わせることを提案します。」

## 演習

次の状況について、問題点を3つ挙げ、それぞれの改善案を考えてください。

> あるサービスでは、画面ごとに担当者が違い、ボタンの角の丸み、主要ボタンの色、エラーメッセージの位置がそれぞれ異なっている。色の指定は `#2F6FED` のような値が各画面のコードに直接書かれている。共通部品の資料はあるが、見た目の画像だけが載っている。

??? note "解答例"
    - 主要ボタンの色やエラーの位置が画面ごとに違い、学習を再利用できない。共通部品にそろえ、役割ごとの見た目を統一する
    - 色の値が直接書かれており、変更や統一ができない。`color-action-primary` のように役割で名付けたトークンに置き換える
    - 共通部品の資料に見た目しかなく、使い方の判断が人によって違う。使う場面と使わない場面、状態ごとの見た目、文言、アクセシビリティの要件を追記する
