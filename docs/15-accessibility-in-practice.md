# 第15章 アクセシビリティ実践編
## 第15章 アクセシビリティ実践編

アクセシビリティは、抽象的な理想ではなく、具体的な不備を直す実践です。見えている人だけを前提にしたUIは、キーボード操作、読み上げ、低視力、色覚差、認知負荷の観点で簡単に破綻します。ここでは、実務で起きやすい問題をどう修正するかを整理します。

## 1. よくある不備は派手ではなく地味である

アクセシビリティの問題は、大きな崩れとして現れるとは限りません。むしろ、見た目では気づきにくい小さな不備が利用不能につながります。

よくある例:

- ラベルがなく、プレースホルダーだけで入力させる
- フォーカス位置が分からない
- エラーが色だけで示されている
- 見出し構造が曖昧で読み上げ順が崩れる

どれも画面を一見しただけでは問題が分かりにくい点が厄介です。

この見えにくさを前提にすると、まずは利用不能につながりやすい箇所から順に確認するのが有効です。次は、フォームで起きやすい問題から見ます。

## 2. フォームでは意味が残ることが重要である

フォームで重要なのは、入力中も項目の意味が失われないことです。プレースホルダーだけに頼ると、入力を始めた途端に文脈が消えます。

必要な改善:

- 常設ラベルを置く
- 必須か任意かを明示する
- エラーは文言でも説明する

「赤くしたから伝わるはず」という考え方は危険です。色が見えにくい人にも、読み上げ環境にも伝わりません。

## 3. フォーカスはキーボード利用者の視線である

マウス中心で確認していると、フォーカス表示を見落としがちです。しかし、キーボード操作ではフォーカスが今どこにあるかが唯一の手がかりになることがあります。

見るべき点:

- フォーカスリングが十分見えるか
- 背景と区別できるか
- フォーカス順が視覚順と一致しているか

フォーカスを消す装飾は、見た目を整える代わりに操作可能性を壊していることがあります。

## 4. 色だけに依存しない

状態表示では、成功、警告、エラーを色で分けたくなります。しかし、色だけでは意味が伝わらない場面があります。

対策:

- アイコンやラベルを併用する
- 文言で状態を明示する
- コントラストを確保する

色は補助的な手段であり、唯一の手がかりにしてはいけません。

コントラストには、具体的な基準があります。WCAGのレベルAAでは、次の値が求められます。

| 対象 | 必要なコントラスト比 |
| --- | --- |
| 通常の文字 | 4.5:1 以上 |
| 大きな文字（おおむね24px以上、または太字で19px程度以上） | 3:1 以上 |
| 入力欄の枠線、アイコン、フォーカス表示など文字以外の部品 | 3:1 以上 |

薄い灰色の補足文字や、淡い色の入力欄の枠線は、この基準を満たしていないことがよくあります。デザインツールやブラウザの開発者ツールには、コントラスト比を確認する機能があります。

## 5. 読み上げと構造を意識する

アクセシビリティは見た目の改善だけでは終わりません。見出し、ラベル、ボタン名、順序といった構造が整理されている必要があります。

例:

- 見出しで画面構造が追えるか
- ボタン名だけで役割が分かるか
- 同じ文言のリンクが並びすぎていないか

視覚的には整っていても、読み上げでは「こちら」「詳細」ばかり並ぶ画面は使いにくくなります。

構造を支える手段として、HTMLだけでは足りない部分を補うのがARIAです。次は、その使い方を見ます。

## 6. ARIAは最小限に使う

ARIAは、HTMLだけでは伝えきれない役割や状態を、スクリーンリーダーなどの支援技術に伝えるための属性です。便利ですが、誤って使うと、何も付けないより悪い結果になることがあります。

基本の考え方:

- まず、適切なHTMLの要素を使う。ボタンには `button`、リンクには `a`、見出しには `h1`〜`h6` を使えば、多くの情報は自動的に伝わる
- `div` にクリックの処理を付けてボタンの代わりにすると、キーボード操作も役割の伝達も自分で実装する必要が出る
- HTMLで表現できない状態だけを、ARIAで補う

よく使うARIAの例:

| 属性 | 使う場面 |
| --- | --- |
| `aria-label` | アイコンだけのボタンに、名前を付ける |
| `aria-describedby` | 入力欄と、補足説明やエラーメッセージを結びつける |
| `aria-invalid` | 入力欄にエラーがあることを伝える |
| `aria-current` | ナビゲーションやステップ表示で、現在の位置を伝える |
| `aria-sort` | 表の列の並び順を伝える |
| `aria-live`、`role="status"` | 画面の一部が更新されたこと（保存完了、件数の変化など）を読み上げさせる |

## 7. 確認の手順を決めておく

アクセシビリティの問題は、見た目を眺めるだけでは見つかりません。次の手順を、画面ができるたびに短時間で行う習慣を作ると、多くの不備を早い段階で見つけられます。

1. マウスを使わず、Tabキーと Enter、Space、矢印キーだけで主要な操作を最後まで行う
2. その間、フォーカスの位置が常に見えているか、順番が自然かを確かめる
3. ブラウザの表示を200%に拡大し、文字が切れたり重なったりしないか、横スクロールが必要にならないかを確かめる
4. コントラストを確認するツールで、文字と部品の色を確かめる
5. スクリーンリーダー（macOSのVoiceOver、WindowsのNVDAなど）で、見出し、ボタン名、入力欄のラベル、エラーが読み上げられるかを確かめる
6. 端末で「視差効果を減らす」設定にして、大きな動きが止まるかを確かめる

自動でチェックするツールも役に立ちますが、見つけられる問題は全体の一部に限られます。特に、フォーカスの順番が自然か、ボタン名だけで意味が分かるか、といった判断は、人が操作して確かめる必要があります。

ここまでの修正観点を踏まえると、良い改善の条件も整理しやすくなります。次は、実務で判断しやすい基準をまとめます。

## 8. 良いアクセシビリティ改善の条件

良い改善は、次の問いに答えやすい状態です。

- 見え方が違っても意味が伝わるか
- マウスがなくても操作できるか
- 状態変化が文言と構造でも理解できるか

この3つを満たせば、アクセシビリティは付け足しではなく、UI品質の一部になります。

アクセシビリティ不備は、気づきにくい一方で影響が深い問題です。使いにくいではなく、完了できない、意味を誤る、必要情報に到達できないという形で表れます。

- 完了率が下がる: フォーカス不明瞭やラベル不足で、途中で操作不能になる
- 誤解が増える: 色だけの状態表示や曖昧な構造で、重要な意味を取り違える
- 修正機会を失う: エラー内容が伝わらず、直し方が分からない
- 利用者を狭める: 特定条件でしか使えないUIになり、結果的に全体品質も下がる

アクセシビリティ改善は、個別対応ではなく画面品質の底上げとして扱うべきです。最後に、この章の要点をまとめます。

## 9. この章の要点

- アクセシビリティ不備は小さく見えても利用不能につながる
- フォームではラベル、文言、エラー説明を残す
- フォーカス表示はキーボード操作の手がかりである
- 色だけに依存せず、構造と文言でも状態を伝える
- コントラストは基準の値で確かめる
- ARIAはHTMLで表現できない部分だけを補う
- キーボード操作、拡大、読み上げの確認を習慣にする

## 迷いやすい判断

**自動チェックツールで問題がなければ十分か**

十分ではありません。自動チェックツールが見つけられるのは、コントラスト不足や代替テキストの欠落など、機械的に判定できる問題に限られます。フォーカスの順番が自然か、ボタン名だけで意味が分かるか、エラーの内容が理解できるか、といった判断には、人が実際に操作して確かめる手順が必要です。

**カスタムの部品を作るか、標準の部品を使うか**

標準のHTML要素（`button`、`select`、`input type="checkbox"` など）は、キーボード操作や読み上げへの対応が組み込まれています。見た目を変えたいだけなら、標準の要素のままCSSで装飾します。独自の部品を作る場合は、キーボード操作、役割、状態の伝達をすべて自分で実装する必要があります。

## レビューコメントの例

「補足説明の文字色が `#B0B0B0` で、白い背景とのコントラスト比が約2.2:1しかありません。WCAGのAAで求められる4.5:1に届かず、読みにくい人がいます。`#6B6B6B` 程度まで濃くすることを提案します。」

「保存後の『保存しました』の表示がスクリーンリーダーで読み上げられず、保存できたかどうかが伝わりません。表示する領域に `role="status"` を付けると、内容の変化が読み上げられます。」

## 演習

次のログイン画面について、この章の確認手順（キーボード、拡大、コントラスト、読み上げ）で見つかりそうな問題を挙げてください。

> メールアドレスとパスワードの欄はプレースホルダーだけで項目名を示している。「ログイン」は `div` 要素にクリックの処理を付けて作られている。パスワードの表示切り替えは目のアイコンだけ。エラーは入力欄の枠線が赤くなるだけ。

??? note "解答例"
    - キーボード: `div` のログインボタンにはTabキーで移動できず、Enterでも押せない。`button` 要素にする
    - 読み上げ: 入力欄の名前がプレースホルダーだけで、入力後は読み上げられない。目のアイコンにも名前がない。`label` を付け、アイコンには `aria-label="パスワードを表示"` を付ける
    - コントラストと色: エラーが赤い枠線だけで、色の区別が難しい人や読み上げの利用者に伝わらない。エラーの文言を表示し、`aria-describedby` で入力欄と結びつける
