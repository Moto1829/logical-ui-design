# ユーザビリティテストの簡易手順
## ユーザビリティテストの簡易手順

第7章と第17章では、設計者やチームが画面を見て評価するレビューを扱いました。レビューは早く安く問題を見つけられますが、見つけられるのは評価する人が想像できる問題に限られます。実際の利用者に操作してもらうユーザビリティテストを組み合わせると、想像していなかった迷い方や誤解を見つけられます。

この資料では、専用の設備や大きな予算がなくても実施できる、少人数での簡易的なテストの手順をまとめます。

## 1. 少人数でも多くの問題が見つかる

ユーザビリティテストというと、大人数を集める調査を想像するかもしれません。しかし、使い方の問題を見つける目的であれば、5人程度でも主要な問題の多くが見つかると言われています。

理由は、同じ問題には多くの人が同じようにつまずくからです。3人目、4人目になると、同じ箇所で同じように迷う様子が繰り返し観察されます。

そのため、一度に大人数でテストするより、少人数のテストと修正を何度も繰り返す方が効果的です。

## 2. 準備する

### 目的を1つに絞る

「使いやすいかどうか」のような広い目的では、何を観察すればよいかが決まりません。次のように、確かめたいことを具体的にします。

- 初めての人が、会員登録を完了できるか
- 絞り込みの機能を見つけて使えるか
- 請求書のダウンロード方法が分かるか

### タスクを作る

参加者に依頼する作業を、2〜5個程度用意します。タスクは、画面の言葉を使わずに、目的として書くのがコツです。

| 悪いタスク | 良いタスク |
| --- | --- |
| 「フィルタ」ボタンを押して、ステータスを「未対応」にしてください | まだ誰も対応していない問い合わせだけを見たいとします。探してみてください |
| 設定画面から通知をオフにしてください | 毎朝届くメールを止めたいとします。どうしますか |

画面の言葉をタスクに入れると、参加者はその言葉を画面の中で探すだけになり、本当に分かりやすいかどうかを確かめられません。

### 参加者を集める

実際の利用者、または利用者に近い人を選びます。社内で集める場合は、そのサービスの開発や企画に関わっていない人を選びます。作り手は、画面の構造を知りすぎているからです。

### 準備物

- テストする画面（完成品でなくてもよい。試作品や紙の画面でもよい）
- タスクを書いたカード
- 記録用のメモ用紙、または画面と音声の録画（参加者の同意を得る）
- 終了後の簡単な質問

## 3. 実施する

### 始める前に伝えること

- テストしているのは画面であり、参加者の能力ではないこと
- 迷ったり、うまくいかなかったりしても問題ないこと
- 考えていることを声に出しながら操作してほしいこと
- いつでも中断できること

考えていることを声に出してもらう方法は、思考発話法と呼ばれます。「今、どこを押そうか迷っています」「これは保存ボタンだと思った」のような発言から、画面のどこで何を誤解したのかが分かります。

### 進行中に気をつけること

- 参加者が迷っても、すぐに助けない
- 「どこを押せばよいですか」と聞かれたら、「どこだと思いますか」と返す
- 画面について説明したり、言い訳をしたりしない
- 参加者の発言と、実際の操作の両方を記録する

迷っている時間こそが、観察すべき問題です。助けてしまうと、その問題は見えなくなります。ただし、参加者が強い不安を感じている場合や、長く止まってしまった場合は、次のタスクに進みます。

### 記録すること

| 記録する内容 | 例 |
| --- | --- |
| タスクを完了できたか | 完了、助けがあれば完了、完了できない |
| つまずいた場所 | 絞り込みのボタンを見つけるまでに30秒かかった |
| 発言 | 「この『適用』は何に適用されるんだろう」 |
| 予想と違った操作 | 保存ボタンではなく、右上の×を押した |

## 4. 結果をまとめる

テストが終わったら、記録をもとに問題を整理します。

1. 観察された問題を、1件ずつ書き出す
2. 同じ問題をまとめ、何人がつまずいたかを数える
3. 問題の重さを判断する（完了できない、時間がかかった、気になる点の3段階など）
4. 問題ごとに、関係する原則と改善の方向を書く

問題の書き方は、第7章で扱ったレビューコメントの形がそのまま使えます。

例:

「5人中4人が、絞り込みボタンを見つけるまでに20秒以上かかりました。ボタンが一覧の右下にあり、一覧の上部を見ている参加者の視線に入っていません。一覧の上部、検索欄の隣に移動することを提案します。」

参加者の意見（「色を青にした方がいい」など）は、そのまま採用するのではなく、その意見の背景にある問題（「どこが押せるか分かりにくかった」など）を読み取ります。

## 5. よくある失敗

- 誘導してしまう: 「このボタンは分かりやすいですか」のように答えを示唆する質問をする
- 作り手だけで実施する: 自分が作った画面の問題を、冷静に観察するのは難しい。可能なら2人で、進行役と記録役を分ける
- 結果を残さない: 観察した内容がその場の印象で終わり、改善につながらない
- 1回で終わる: 修正後に再びテストしないと、修正が問題を解決したかどうか分からない

## 6. この資料の要点

- 5人程度の少人数のテストでも、主要な問題の多くが見つかる
- タスクは、画面の言葉を使わずに目的として書く
- 参加者が迷っても助けず、考えていることを声に出してもらう
- 結果は、何人がどこでつまずいたかを数え、レビューコメントの形でまとめる
- 少人数のテストと修正を、繰り返し行う
