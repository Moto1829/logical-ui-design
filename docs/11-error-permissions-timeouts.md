# 第11章 エラー、権限不足、タイムアウトの設計
## 第11章 エラー、権限不足、タイムアウトの設計

失敗時のUIは、単に問題を通知するためのものではありません。ユーザーが状況を理解し、次にどう行動すればよいかを示す必要があります。ここでは、エラー、権限不足、タイムアウトといった失敗状態をどう設計するかを整理します。

## 1. 失敗状態にも種類がある

「エラー」と一言でまとめると、必要な支援が曖昧になります。少なくとも次の違いを分けて考えるべきです。

- 入力不備: ユーザーがその場で修正できる
- 権限不足: 自分では解決できない可能性がある
- 通信失敗やタイムアウト: 再試行で回復できる可能性がある
- システム障害: 待つ、問い合わせるなど別の行動が必要

種類が違えば、表示すべき説明も導線も変わります。

まずは種類を分けることが出発点ですが、それだけでは回復を助けられません。次に、ユーザーが行動を決められるだけの説明の出し方を見ます。

## 2. 何が起きたかを曖昧にしない

「エラーが発生しました」は、ほとんど何も伝えていません。重要なのは、ユーザーが取るべき行動を決められるだけの情報を返すことです。

最低限必要な要素:

- 何が起きたか
- 自分で直せるか
- 次に何をすればよいか

悪い例:

- エラーが発生しました

良い例:

- 接続が不安定なため保存できませんでした。通信環境を確認して再試行してください

## 3. 権限不足は責任の所在を明確にする

権限不足は、ユーザーの操作ミスではないことが多いです。それにもかかわらず「アクセスできません」だけだと、何が不足しているのか分からず、行き止まりになります。

権限不足で必要な情報:

- 何にアクセスできないのか
- なぜできないのか
- 誰に依頼すればよいか

例:

- このレポートは管理者のみ閲覧できます。必要な場合は管理者へ閲覧権限を依頼してください

## 4. タイムアウトでは再試行の道を残す

タイムアウトや一時的な通信失敗は、再試行で回復することがあります。そのため、ユーザーを行き止まりにしないことが重要です。

見るべき点:

- いま再試行すればよいのか
- 入力内容は保持されているのか
- 他の操作をすべきなのか

特にフォームでは、失敗時に入力内容が消えると、失敗そのものより大きなストレスになります。

## 5. 失敗時にユーザーを責めない

失敗文言で避けたいのは、ユーザーに責任を押し付ける表現です。ユーザーが悪いのではなく、いま起きている状態を一緒に解決する姿勢が必要です。

避けたい表現:

- 正しく入力してください
- 操作に失敗しました
- 不正な操作です

より良い表現:

- メールアドレスの形式で入力してください
- 接続が不安定なため保存できませんでした
- この操作には管理者権限が必要です

こうした文言の違いが積み重なると、失敗状態は混乱ではなく回復の案内になります。次は、良い失敗状態が満たすべき条件を整理します。

## 6. 良い失敗状態の条件

良い失敗状態は、次の問いに答えやすい状態です。

- 何が起きたか
- いま自分で解決できるか
- 次に何をすればよいか

この3つが分かれば、失敗状態は混乱の原因ではなく、回復の起点になります。

失敗状態の案内が弱いUIでは、ユーザーは失敗そのものより、その後どうすればよいか分からないことに強く消耗します。作業中断や再入力、問い合わせ増加にもつながります。

- 回復できずに止まる: 再試行すべきか別手段を取るべきか判断できない
- 自責感が生まれる: 曖昧なエラー文言で、自分の操作が悪いと思い込む
- 再入力負荷が増える: 入力保持がなく、失敗のたびに最初からやり直す
- サポート依存が増える: 権限不足や障害の切り分けができず、問い合わせが必要になる

失敗時のUIは、問題の通知ではなく回復支援として設計する必要があります。最後に、この章の要点をまとめます。

## 7. この章の要点

- 失敗状態は種類ごとに分けて設計する
- 何が起きたか、どう回復するかを具体的に示す
- 権限不足とタイムアウトでは必要な支援が違う
- ユーザーを責めず、次の行動を示す

## 迷いやすい判断

**エラーの技術的な詳細を表示するか**

利用者向けのメッセージには、何が起きたか、どうすればよいかを、利用者の言葉で書きます。エラーコードなどの技術的な詳細は、問い合わせのときに役立つので、本文とは分けて小さく表示するか、折りたたんで表示します。技術的な詳細だけを表示すると、利用者は何もできません。

**権限のない機能を表示するか、隠すか**

その機能があることを知っておくと役立つ場合（管理者に頼めば使える、など）は、表示したうえで、権限がないことと、誰に依頼すればよいかを示します。利用者に関係のない機能（他の部署専用の機能など）は、隠して画面を簡潔に保ちます。

## レビューコメントの例

「権限のない画面を開くと『403 Forbidden』とだけ表示されます。利用者は何が起きたのか、どうすれば見られるのか分かりません。『このページを見る権限がありません。管理者の〇〇さんに依頼してください』のように、原因と依頼先を示すことを提案します。」

「入力中にセッションが切れると、保存ボタンを押した時点でログイン画面に移り、入力内容が失われます。期限が近づいたら知らせて延長できるようにするか、再ログイン後に入力内容を復元してはどうでしょうか。」

## 演習

次のエラー画面について、問題点を3つ挙げ、改善した文言を考えてください。

> 決済の途中で通信がタイムアウトした。画面には「エラー（E5021）」とだけ表示され、ボタンは「OK」の1つだけ。OKを押すとトップページに戻る。

??? note "解答例"
    - 何が起きたかが分からない。「通信に時間がかかり、決済を完了できませんでした」と書く
    - 決済されたのかどうかが分からず、もう一度払うと二重に請求されるのではと不安になる。「お支払いは確定していません」のように、状態を明示する
    - トップに戻るしか選択肢がない。「もう一度試す」ボタンを置き、入力内容を保持する。エラーコードは問い合わせ用に小さく添える
