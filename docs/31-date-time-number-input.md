# 第31章 日付、時刻、数値の入力
## 第31章 日付、時刻、数値の入力

第4章ではフォーム全般を扱いました。この章では、その中でも特に入力ミスと手間が生まれやすい、日付、時刻、数値の入力に絞ります。これらの値は、書き方の形式が人によって違い、単位や桁を誤りやすく、しかも誤りに気づきにくいという特徴があります。

## 1. 入力の部品は値の性質で選ぶ

日付の入力には、カレンダーから選ぶ方法、年・月・日を選択肢から選ぶ方法、直接文字で入力する方法があります。どれが良いかは、入力する値の性質によって変わります。

| 値の性質 | 向く入力方法 | 例 |
| --- | --- | --- |
| 近い将来の日付で、曜日が判断に関わる | カレンダー | 予約日、締め切り |
| 遠い過去の日付で、本人が正確に知っている | 直接入力、または年・月・日の選択 | 生年月日 |
| 期間 | 開始日と終了日をまとめて選べるカレンダー | 宿泊期間、集計期間 |
| よく使う相対的な期間 | 選択肢 | 「今日」「過去7日間」「今月」 |

生年月日をカレンダーで入力させると、数十年前まで月を1つずつさかのぼる必要があり、非常に手間がかかります。逆に、予約日を直接入力させると、曜日を確かめるために別のカレンダーを見ることになります。

## 2. 形式の違いは受け入れる側で吸収する

同じ日付でも、「2026/10/01」「2026-10-01」「2026年10月1日」のように書き方はさまざまです。電話番号のハイフンの有無や、数字の全角と半角も同様です。

入力形式が違うという理由でエラーを返すと、ユーザーは形式を推測して何度も入力し直すことになります。

対策の基本:

- 意味が一意に分かる形式の違いは、システム側で変換して受け入れる
- 全角の数字は半角に、区切り文字の違いは統一して扱う
- 受け入れる形式の例を、入力欄の近くに示す（「例: 2026/10/01」）
- 変換した結果を表示して、意図どおりか確認できるようにする

「ハイフンなしで入力してください」という注意書きは、システムの都合をユーザーに押し付けています。ハイフンを取り除く処理はシステム側で簡単にできます。

ただし、「01/02/2026」のように、1月2日とも2月1日とも読める形式は、変換で吸収できません。このような曖昧さがある場合は、年・月・日を分けて入力させるか、変換結果を「2026年1月2日（金）」のように表示して確認させます。

## 3. 単位と桁を入力欄のそばに置く

数値の入力では、何の単位で入力するのかが分からないことが、桁の誤りにつながります。

確認したい点:

- 単位（円、千円、%、kg など）が、入力欄のすぐ横にある
- 金額の入力で、入力中または入力後に桁区切りが表示される
- 入力できる範囲がある場合は、事前に示されている（「1〜99」）
- 大きな数値では、読み上げやすい表記も併記されている（「1,200,000円（120万円）」）

「千円単位」で入力する欄に、ユーザーが円単位で入力すると、金額は1000倍になります。単位は見出しの中に書くのではなく、入力欄の横に置き、入力するたびに目に入るようにします。

## 4. 時刻とタイムゾーンを明示する

時刻の表示と入力では、次の点が問題になりやすくなります。

- 12時間表記と24時間表記の混在（「12:00 AM」が深夜か正午か迷う）
- 相対表記の曖昧さ（「3日前」がいつなのか、正確な日時が分からない）
- 異なる地域の人が使う場合のタイムゾーン

設計上の示唆:

- 日本語のサービスでは、24時間表記を基本にする
- 「3日前」のような相対表記を使う場合は、正確な日時も確認できるようにする
- 地域をまたいで使われるサービスでは、どのタイムゾーンの時刻かを表示する
- 締め切りのように境界が重要な時刻は、「10月1日 23:59まで」のように明確に書く

「10月1日まで」は、10月1日を含むのか含まないのかが曖昧です。締め切りや有効期限は、日付と時刻の両方を書きます。

## 5. 数値入力の部品を正しく選ぶ

数値を入力する部品にも、向き不向きがあります。

- 数字専用の入力欄: 数量や金額など、計算に使う数値に向く。HTMLの `type="number"` は、マウスのホイール操作で値が変わる、先頭の0が消えるなどの注意点がある
- 数字のキーボードを出すだけの入力欄: 郵便番号、電話番号、カード番号など、数字だが計算しない値に向く。HTMLでは `inputmode="numeric"` を使う
- 増減ボタン付きの入力欄: 1〜10程度の小さな範囲で、少しずつ変える値に向く
- スライダー: 正確な値より、大まかな範囲を感覚的に選ぶ場合に向く

郵便番号や会員番号に `type="number"` を使うと、先頭の0が消えたり、意図しない変換が起きたりします。数字であることと、数値として扱うことは別の問題です。スライダーは、正確な値を入力するのには向かないため、必要なら直接入力できる欄を併用します。

## 6. 良い日付・時刻・数値入力の条件

- 値の性質に合った入力の部品を選んでいる
- 意味が一意に分かる形式の違いを、システム側で受け入れている
- 単位、範囲、形式の例が入力欄のそばにある
- 時刻の表記とタイムゾーン、締め切りの境界が明確である
- 数値として扱う値と、数字で書かれた識別番号を区別している

日付や数値の入力が崩れると、気づきにくい誤りが生まれます。

- 桁を誤る: 単位を取り違え、10倍や1000倍の値を登録してしまう
- 入力を繰り返す: 形式の違いでエラーが続き、正しい形式を探し続ける
- 期限を誤解する: 締め切りの境界やタイムゾーンを取り違え、期限を過ぎてしまう
- 手間が増える: 値に合わない部品で、何度も操作を繰り返すことになる

日付や数値は、誤っていても見た目では分かりにくい値です。最後に、この章の要点をまとめます。

## 7. この章の要点

- 日付の入力方法は、近い将来か遠い過去か、期間かで選ぶ
- 形式の違いはシステム側で吸収し、変換結果を確認できるようにする
- 単位と範囲は入力欄のそばに置き、桁の誤りを防ぐ
- 時刻の表記、タイムゾーン、締め切りの境界を明示する
- 数値として扱う値と、数字で書かれた識別番号を区別する

## 迷いやすい判断

**ブラウザ標準の日付入力を使うか、独自のカレンダーを作るか**

ブラウザ標準の日付入力は、キーボード操作や読み上げへの対応が組み込まれており、モバイルでは端末に合った入力方法が使われる利点があります。見た目を細かく制御できないという弱点はありますが、独自に作る場合は、キーボードだけで操作できること、読み上げで日付と曜日が伝わることまで含めて実装する必要があります。その負担に見合う理由がない限り、標準の入力を優先します。

**相対表記と絶対表記のどちらで表示するか**

新しさが重要な一覧（通知、コメント、更新履歴）では、「5分前」のような相対表記が直感的です。日付そのものが判断に関わる場面（請求、契約、締め切り）では、絶対表記にします。相対表記を使う場合も、正確な日時を確かめる手段を残します。

## レビューコメントの例

「予算の入力欄が『千円単位』で入力する仕様ですが、そのことが表の見出しにしか書かれていません。円単位で入力されると1000倍の金額で登録されます。入力欄の右に『千円』と表示し、入力後に『120万円』のような換算を併記してはどうでしょうか。」

「電話番号の欄でハイフンを入力するとエラーになります。利用者の多くはハイフン付きで入力するため、何度もやり直すことになります。ハイフンや全角数字はシステム側で取り除いて受け入れることを提案します。」

## 演習

次の入力フォームについて、問題点を3つ挙げ、それぞれの改善案を考えてください。

> 会員登録フォームの生年月日欄がカレンダーで、初期表示は今月になっている。郵便番号の欄は `type="number"` で、「半角数字・ハイフンなし」と書かれている。キャンペーンの応募締め切りは「10月31日まで」と表示されている。

??? note "解答例"
    - 生年月日をカレンダーで入力させると、何十年分も月をさかのぼる必要がある。年・月・日の直接入力にする
    - 郵便番号に `type="number"` を使うと先頭の0が消える恐れがある。`inputmode="numeric"` の文字入力欄にし、ハイフンや全角数字はシステム側で変換して受け入れる
    - 「10月31日まで」は、当日を含むのか、何時までなのかが曖昧である。「10月31日（土）23:59まで」のように日時で示す
