# 第27章 AI機能のUI設計
## 第27章 AI機能のUI設計

要約、文章の下書き、分類、質問への回答など、生成AIを使った機能は多くのサービスに組み込まれるようになりました。こうした機能のUIには、これまでの章で扱った原則がそのまま当てはまります。ただし1つだけ大きく違う点があります。同じ操作をしても、毎回同じ結果が返るとは限らず、結果が正しいとも限らないことです。この章では、その性質を前提にしたUIの組み立て方を扱います。

## 1. AIの出力は「確からしい結果」として扱う

保存ボタンを押せば保存され、合計を計算すれば正しい値が返る、というのが従来のUIの前提でした。AIの出力はそうではありません。もっともらしく見えても、事実と異なる内容や、指示と違う内容が含まれることがあります。

このときUIで起きやすい問題は、次の2つです。

- 過信: 出力が完成品のように見えるため、確認せずにそのまま使ってしまう
- 不信: 一度誤りに出会うと、正しい出力まで信用しなくなる

どちらも、出力の性質がUIから読み取れないことが原因です。設計の目標は、ユーザーが出力を「確認して使う素材」として扱えるようにすることです。

設計上の示唆:

- AIが生成した内容であることを明示する
- 出力をそのまま確定させず、ユーザーが採用する操作を挟む
- 誤りがありうることを、出力の近くで短く伝える

画面の隅に「AIは誤った情報を生成することがあります」と小さく書くだけでは、第25章で扱った「関係する場所の近くに出す」原則を満たしていません。注意書きは、確認が必要な出力のすぐそばに置きます。

## 2. 生成中の状態と中断を設計する

AIの生成には数秒から数十秒かかることがあります。第22章で扱った待ち時間の考え方が、ここでも重要になります。

確認したい点:

- 生成が始まったことが、押した直後に分かる
- 文章を少しずつ表示する場合、読み始めてよいのか、まだ変わるのかが分かる
- 生成を途中で止められる
- 止めたときに、途中までの結果が残るのか消えるのかが分かる

途中で止められることは特に重要です。生成の冒頭を見ただけで、指示が伝わっていないと気づくことはよくあります。最後まで待たないとやり直せない設計は、ユーザーの時間を奪います。

## 3. 根拠と範囲を見せる

ユーザーが出力を確認するには、確認の手がかりが必要です。

手がかりの例:

- 参照した資料や文書へのリンク
- 要約の場合、元の文章のどこから取ったか
- 対象にした範囲（「直近30日のチケット120件を要約」）
- 処理できなかった部分（「添付ファイル2件は読み取れませんでした」）

数値で確信度を示す方法もありますが、利用者にとって「82%」がどれくらい信頼できるのかは判断しにくいものです。多くの場合、数値よりも「どこを見れば確かめられるか」を示す方が、確認の行動につながります。

逆に、根拠がない出力に、根拠があるかのような見た目を与えてはいけません。存在しない出典をリンク風に表示することは、第26章で扱ったダークパターンと同じく、ユーザーの判断をゆがめます。

## 4. 結果は編集、再生成、取り消しができるようにする

AIの出力は下書きとして扱い、ユーザーが手を入れられるようにします。

基本となる操作:

- 採用する: 出力を本文や入力欄に反映する
- 編集する: 反映前、または反映後に手直しする
- 再生成する: 同じ指示、または指示を変えてもう一度生成する
- 元に戻す: 反映した結果を取り消し、生成前の状態に戻す

特に既存の内容を書き換える機能では、何がどう変わるのかを見せることが重要です。文章の書き換えであれば、変更箇所を差分として表示し、部分ごとに採用するかどうかを選べるようにすると、ユーザーは安心して使えます。

第13章で扱ったとおり、取り消せない操作ほど慎重な設計が必要です。AIがメールを送信する、データを削除する、といった外部に影響する操作では、実行前に内容を確認する段階を必ず置きます。

## 5. 入力の手がかりを与える

自由に文章を入力できる欄は、何でもできるように見える反面、何を入力すればよいか分からない欄でもあります。第10章で扱った空状態と同じく、最初の一歩を示す必要があります。

対策の基本:

- 入力例や、よく使われる指示の候補を示す
- できることと、できないことを短く伝える
- 画面の文脈を自動で引き継ぐ（開いている文書を対象にするなど）
- できない依頼に対しては、理由と代わりの方法を返す

「何でも聞いてください」という案内は、範囲が分からないため、かえってユーザーを迷わせます。「この議事録の要点、決定事項、次のアクションをまとめられます」のように、その場で役に立つ使い方を具体的に示します。

## 6. 良いAI機能UIの条件

- AIが生成した内容であることが分かり、確認が必要なことが出力の近くで伝わる
- 生成中であることが分かり、途中で止められる
- 確認のための根拠や対象範囲が示されている
- 出力を採用、編集、再生成、取り消しできる
- 何を依頼できるかが、具体例で示されている

AI機能のUIが崩れると、機能の精度とは別のところで体験が損なわれます。

- 誤りが広がる: 確認されないまま、誤った出力が文書やメールに使われる
- 使われなくなる: 一度の誤りで信用を失い、機能そのものが避けられる
- 時間を奪う: 的外れな生成を最後まで待ち、最初からやり直すことになる
- 取り返しがつかない: 確認を挟まずに外部へ影響する操作が実行される

AIは強力な道具ですが、出力を判断するのはユーザーです。UIの役割は、その判断を助けることにあります。最後に、この章の要点をまとめます。

## 7. この章の要点

- AIの出力は、確認して使う素材としてUIに表す
- 生成中の状態を見せ、途中で止められるようにする
- 確認のための根拠と対象範囲を示し、根拠のない見た目を与えない
- 採用、編集、再生成、取り消しの操作をそろえる
- 自由入力欄には、具体的な依頼の例を添える

## 迷いやすい判断

**AIの出力を自動で反映するか、提案にとどめるか**

失敗しても影響が小さく、すぐに元に戻せるもの（入力欄の補完候補、タグの提案など）は、自動で反映してもかまいません。一方、文書の本文、他人に送られる内容、データの変更を伴うものは、提案として示し、ユーザーが採用する操作を挟みます。判断の軸は、第13章と同じく「誤ったときの影響」と「戻せるかどうか」です。

**AIであることを、どの程度強く表示するか**

ラベルやアイコンで控えめに示すのが基本です。ただし、人が書いたものと区別がつかないと困る場面（他人に送るメッセージ、公開される文章など）では、編集画面で明確に区別できるようにします。過剰な警告を毎回出すと、第25章で扱った通知疲れと同じく、読まれなくなります。

## レビューコメントの例

「要約結果が通常の本文と同じ見た目で表示され、そのまま保存されます。AIが生成した内容と分からず、確認されずに共有される恐れがあります。要約は下書きとして区別して表示し、『本文に追加』の操作で反映するようにしてはどうでしょうか。」

「生成中は画面全体の操作がロックされ、停止する手段がありません。指示が意図と違うと気づいても最後まで待つ必要があります。生成中に停止ボタンを表示し、途中までの結果を残せるようにすると、やり直しの時間を減らせます。」

## 演習

次の画面について、問題点を3つ挙げ、それぞれの改善案を考えてください。

> 問い合わせ管理画面に「AIで返信」ボタンがある。押すと10秒ほど画面全体にスピナーが表示され、その後、生成された返信文が顧客に自動で送信される。送信後に「返信しました」とトーストが表示される。

??? note "解答例"
    - 生成した返信文が確認されずに送信される。外部に影響する操作なので、送信前に下書きとして表示し、編集してから送信できるようにする
    - 生成中に画面全体がロックされ、停止できない。処理中の範囲だけに表示を絞り、停止ボタンを置く
    - 返信の根拠（参照した過去の対応履歴やヘルプ記事）が分からない。下書きの近くに参照元を示し、内容を確認しやすくする
